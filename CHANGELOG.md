# CHANGELOG for 2.2

This changelog consists of the bug & security fixes and new features being included in the releases listed below.

## **v2.2.8 (Upcoming)**

* [fixed] Fixed the lead record's change-log panel printing a date as `جمعة نوفمبر 27, 2026` — a weekday and a Latin comma, in an order this product does not use — while the `2 نوفمبر 2026 في 1:57 ص` beside it on the same screen reads day, month, year. `AttributeValueRepository::getAttributeLabel()` formatted a `date` attribute with `D M d, Y`: `D` is a weekday name the product's date-only format has no slot for, and `d, Y` is the ASP.NET-ish ordering with a comma between the day and the year. Measured on a real call against the seeded `expected_close_date` attribute, before and after: `ar` went `جمعة نوفمبر 27, 2026` → `27 نوفمبر 2026`, `en` went `Fri Nov 27, 2026` → `27 Nov 2026` — `d M Y`, the format `QuoteDataGrid`, `LeadDataGrid`, `EventDataGrid`, the date attribute view and the quote PDF already use, and the one `core()->formatDate()` defaults to minus the clock, so the locale still decides the month name and nothing is special-cased for Arabic. The two sibling branches carrying the same weekday-and-comma pattern (`datetime`, and the `Carbon` fallback in `default`) now render `d M Y H:i A` for the same reason. `Automation/Helpers/Entity/AbstractEntity` and the `Lead` model's `closed_at`/`expected_close_date` casts still name `D M d, Y`; they render automation placeholders and serialised model output rather than this panel, and were left alone deliberately.

* [fixed] Fixed the same panel printing `$0.00` / `$45,000.00` where every other price in the product reads `US$`. The change log stores a *rendering*, not a value — `LogsActivity` writes `old.label` and `new.label` once, at write time, and the panel prints them verbatim — so the currency work that renamed the symbol `Core::formatBasePrice()` emits left the rows written before it untouched: on the reference instance 72 labels across 36 `type = 'system'` rows still carry the pre-`US$` shape, all written in one two-second demo-seeding window on `2026-11-02 01:57` while the instance was still `en`, and `2026_11_05_150000_translate_activity_log_to_arabic.php` skipped them on purpose because a price label is not English *because of the locale*. `2026_11_05_170000_repair_stale_change_log_labels_and_footer.php` re-renders them through `Core::formatBasePrice()` itself, so a repaired label cannot drift from what a fresh write stores — verified byte-for-byte against `getAttributeLabel()` for the same values — and re-renders the 27 date labels the same writer froze in the shape above, because otherwise the panel would keep both shapes on one screen after the code fix. Matching is exact, never a loose pattern: a label moves only while it is byte-for-byte the stale or the current rendering of the row's own `value`, only on `type = 'system'` rows, and a value that cannot be resolved (a date that no longer parses, a money column whose base currency did not render with `$`) is left exactly as it is. Measured on a scratch database holding real copied rows: 63 rows and 99 labels changed on the first run, a forced second execution of `up()` changed nothing, `down()` restored all 405 payloads to a digest identical to the one before `up()`, and a footer row carrying an operator's own wording was skipped in both directions. The date half runs only on an Arabic surface, because the shape it matches is Arabic and rewriting it into another locale's month names is not the repair's call.

* [fixed] Fixed the Arabic admin's footer reading `Powered by … Sijilna.` while the login page two clicks away reads `مدعوم من Sijilna.`. The footer prints a *stored* setting — `general.settings.footer.label`, through `core()->getConfigData()` and `core()->sanitizeHtml()` — so it cannot follow the interface locale the way the login page's translated string does, and the product shipped the English wording as both the config default (`BrandingServiceProvider::overrideFooterCredit()`) and the value `php artisan sijilna:brand` seeds. `Sijilna\Brand\Brand::FOOTER_CREDIT` is now the Arabic credit, so a new install seeds and defaults to it with no row at all, and the English wording that shipped before is kept as `FOOTER_CREDIT_EN` because it is the only record of what an untouched row on an existing installation holds. The same migration as the labels above brings such a row over — matched on the value *as the repository stored it* (`core()->sanitizeHtml()`, so `rel="noreferrer noopener"` and the normalised inline styles have to match too), never on a row an operator edited, and a second run is a no-op. Measured on the live instance: the row held `Powered by <span …>Sijilna</span>.`, now holds `مدعوم من <span …>Sijilna</span>.`, and a real authenticated `GET /admin/leads` (200) renders `<p>مدعوم من <span style="color:rgb(11,60,93);"><a href="https://sijilna.com" target="_blank" rel="noreferrer noopener">Sijilna</a></span>.</p>`, the same words the login page shows.

* [fixed] Fixed a wrong HTTP method on any admin route answering 500 instead of 405. `packages/Webkul/Admin/src/Exceptions/Handler.php` lets a whitelist of statuses through to the branded page — `BRANDED_ERROR_CODES` — and resolves anything outside it to the generic 500, so `MethodNotAllowedHttpException`, which carries a 405, was reported as a server fault: the visitor read "500 internal server error" for what was really a method problem. Measured on the live instance, all answering 500 before this change and 405 after it — a method mismatch is decided by the router before any middleware runs, so the signed-in and anonymous visitor got the same answer: `GET /admin/settings/marketing/events/edit` (that path exists only as `DELETE .../events/{id}`, with `edit` in the id position), `GET /admin/logout`, `POST /admin/logout`, `DELETE /admin/dashboard` and `PUT /admin/leads`; `GET /admin/does-not-exist` answered 404 throughout. `405` joins the constant and gains its own copy in both locales (`405 الطريقة غير مسموح بها` / `405 Method Not Allowed`), because a status the page has no copy for is still coerced to 500 — the whitelist and the copy have to move together. It also joins `$jsonErrorMessages`, so a request that expects JSON receives JSON with a 405 and its own status rather than the generic wording. Only `ar` and `en` carry the copy; the other eight locales fall back to the English string, which renders the title rather than a raw key.

* [fixed] Fixed the address form requiring a region for the countries that ship no region list, which made every seeded quote unsavable. `AttributeForm` required `<attribute>.state` for every country, while the address component renders the region as a `<select>` fed from `country_states` when the chosen country has rows there and as a free-text input with no rule when it does not — and 239 of the 255 seeded countries have no rows, so the free-text branch is the common case, not the exception. * [fixed] Fixed a quote whose adjustment is negative being impossible to save at all. `AttributeForm` validates a `price` attribute with `Decimal`, which refuses a sign, while the browser-side `decimal` rule accepts one (`^[-+]?…`) — so the server rejected a value the form itself had loaded and handed back, and the demo tenant's own third quote stores `-1500.0000`. `Webkul\Core\Contracts\Validations\SignedDecimal` now carries `Decimal`'s shape plus an optional leading `-` or `+`, and an attribute reaches it only by carrying `validation = 'signed_decimal'`, which `AttributeForm` maps for a `price` attribute and nothing else maps at all. Every other money field keeps the non-negative rule, which is the point: widening `Decimal` would have let a negative price, discount, tax or lead value through everywhere at once. The lookahead in the pattern keeps a sign meaningful, because `\d*` alone would let a bare `-` through and MySQL cannot store that in a decimal column, and a non-scalar value fails the rule instead of throwing. The seeded `adjustment_amount` attribute carries the value — a fresh install gets it from `AttributeSeeder` — and `2026_11_05_160000_repair_seeded_quote_data.php` sets it on an installation seeded earlier, matching the seeded row and only while it still holds `decimal`.
